# yadbe — Implementation plan

Statuses: ⬜ to do · 🟦 in progress · ✅ done.

One task = one sub-session = one or more Conventional Commits on the development branch (no PR for now). The master session breaks the work down, starts the sub-sessions, reviews their result and updates this file. A milestone ends with a manual validation by the product owner (checklist in `docs/validation/Mx.md`).

The **Session** column gives the model and effort the sub-session runs with: `opus` for design-heavy or risky backend work (drivers, concurrency, security, edit planning), `sonnet` for ports from yaggui and UI built on a frozen IPC contract. A task whose contract others depend on pushes the contract (Rust types + generated bindings + mock) first.

M2 and M3 are refined at the end of the previous milestone, once the base code is known.

Wave 1 notes: store migrations are v3 (saved queries) and v4 (SSH tunnels). Open after M3-5: P-07 at CPU ×4 is 67–72 ms (was 78–84 ms, target 50 ms); a refresh after a DDL notice does not re-describe an open table tab.

Wave 2 notes: store migrations are v5 (change journal) and v6 (pinned objects); M3-10 needed none. `ApplyOutcome` gained `conflicted` and `journalId`, and `ChangeSet.deletes` is `RowDelete[]`: M3-7 must send `CellUpdate.original` and `RowDelete.values` to get the same checks and journaling. Open after wave 2: SQL Server import runs at about 1.6k rows/s (multi-row `INSERT` capped at 2 100 parameters) against 34–54k on the other engines, so a bulk path is a follow-up; the 1 GiB import memory test was never run; a PostgreSQL import writes three statement-log lines per batch and evicts older entries; explain analyze is not recorded in the history; remembered parameter values do not survive a restart; rebuilt DDL has no `COMMENT ON`, no PostgreSQL aggregates, and assumes a 1,1 identity on SQL Server; MariaDB paths (plans, dependents, JSON checks) are untested.

Open performance points carried from M2: P-09 (idle RAM ≈ 486 MB on WebKitGTK against 300 MB, to measure on WKWebView / WebView2) and one horizontal frame over 32 ms per run in the WebKitGTK grid scroll.
