# Releasing

Ported from yaggui's release tooling. The [`Release`](../.github/workflows/release.yml) workflow builds the installers of every platform. A `vX.Y.Z` tag attaches them to a **draft** GitHub Release; a pull request that touches the packaging (the workflow, `scripts/version.mjs`, `scripts/updater-manifest.mjs`, `scripts/updater-key.mjs`, `src-tauri/tauri.conf.json`) only builds them and keeps them as workflow artifacts. A pull request whose only packaging change is the version checks it without building. The workflow can also be started by hand (Actions → Release → Run workflow): it then builds without releasing.

Nothing is released until the owner has done the [one-time setup](#one-time-setup-by-the-owner): a tag pushed before that fails at its first job (no updater public key).

## Cutting a release

1. Set the version, commit it and push it to the development branch:
   ```bash
   pnpm release:version 0.2.0   # package.json, src-tauri/tauri.conf.json, src-tauri/Cargo.toml, src-tauri/Cargo.lock
   git commit -am 'chore(release): 0.2.0'
   ```
   Versions are plain `X.Y.Z`: the Windows MSI bundler rejects pre-release suffixes.
2. Tag that commit and push the tag:
   ```bash
   git tag v0.2.0
   git push origin v0.2.0
   ```
3. The workflow checks that the tag matches the version of the four files and that the updater public key is set, builds every platform, then creates a draft release with the installers, the update manifest `latest.json`, a `SHA256SUMS.txt` and notes generated by GitHub from the commits and pull requests since the previous tag.
4. Check the draft (notes, assets, sizes), install it on each OS ([`validation/M3.md`](validation/M3.md), "First real release"), then publish it. The Homebrew and AUR channels and the in-app update check follow **published** releases only.

If a build fails, the release is not created: fix, delete the tag (`git push origin :v0.2.0`, `git tag -d v0.2.0`) and tag again. To rebuild a tag whose draft already exists, delete the draft first.

## Artifacts

| Platform | Runner | Files |
|---|---|---|
| macOS Apple Silicon | `macos-latest` | `yadbe_<version>_aarch64.dmg`, `yadbe_<version>_aarch64.app.tar.gz` (updater) |
| macOS Intel | `macos-latest` (cross-compiled) | `yadbe_<version>_x64.dmg`, `yadbe_<version>_x64.app.tar.gz` (updater) |
| Linux x86_64 | `ubuntu-22.04` | `yadbe_<version>_amd64.deb`, `yadbe-<version>-1.x86_64.rpm`, `yadbe_<version>_amd64.AppImage` (also the updater bundle) |
| Windows x64 | `windows-latest` | `yadbe_<version>_x64-setup.exe` (NSIS), `yadbe_<version>_x64_en-US.msi` (both also updater bundles) |

Plus `latest.json`, the update manifest (see [Updates](#updates)), and `SHA256SUMS.txt`.

Linux is built on the oldest supported Ubuntu so the binaries run on older glibc. Release binaries are built without a cache, from a clean state.

## Updates

The app can check for a newer version. The check is **opt-in** (SPEC §1: no network call but the user's connections and, opt-in, update checks): asked once at the first launch of a release build, then in Preferences → About ("Check for updates at startup"), plus "Check for updates" in the palette and next to the version in Preferences → About. While the preference is off, yadbe sends no request; a check asked from the palette or the preferences runs whatever the preference says. The check reads `https://github.com/SimonVanMello/yadbe/releases/latest/download/latest.json`, which always points to the newest **published** release, with yadbe's name and version as the user agent and nothing else.

What it offers depends on how the copy was installed ([`src-tauri/src/updates.rs`](../src-tauri/src/updates.rs)):

| Installed from | Offer |
|---|---|
| Windows installer (`.exe`, `.msi`), macOS `.dmg` or Homebrew cask, AppImage | "Update and restart": the [Tauri updater](https://v2.tauri.app/plugin/updater/) downloads the bundle, checks its signature, installs it and restarts. The cask declares `auto_updates true`, so `brew upgrade` leaves the app to its updater. On Windows the installer runs in passive mode (a progress window, no questions) |
| `.deb` | "Download": the app downloads `yadbe_<version>_amd64.deb` into its cache folder, checks it against `SHA256SUMS.txt`, then shows `sudo apt install <file>` to copy and run in a terminal, and "Restart yadbe" |
| `.rpm` | Same with `yadbe-<version>-1.x86_64.rpm` and `sudo dnf install <file>` (`sudo zypper install --allow-unsigned-rpm <file>` without dnf) |
| AUR (`yadbe-bin`) | "Show the command": `yay -S yadbe-bin` or `paru -S yadbe-bin`, whichever is installed (else the AUR's own `git clone` + `makepkg -si`) |
| Development build, or a binary run in place | "Open the release page" |

Unlike yaggui, yadbe has no integrated terminal: the package manager command is shown and copied, never run by yadbe. The backend chooses it, the frontend never sends one.

A build whose `plugins.updater.pubkey` is empty (any build from the repository before the setup below, a fork's build) is **not configured**: it never asks the question, the preference is disabled with the reason, and a check on demand answers "Updates are not available in this build" without any request.

[`scripts/updater-manifest.mjs`](../scripts/updater-manifest.mjs) writes `latest.json` from the updater bundles and their `.sig` files; the release job fails rather than publish a manifest that leaves a platform out. The updater bundles are signed with a minisign key, unrelated to Apple or Windows code signing. `plugins.updater.requireSignedVersion` is `true`: an installed copy only accepts a bundle whose signature was made for the version the manifest announces (`tauri build` records it), so a tampered manifest cannot pair a new version number with an older, validly signed bundle. Keep it on: [`scripts/updater-key.mjs`](../scripts/updater-key.mjs) refuses a tag build without it.

## Package managers

Each channel has its own workflow, triggered when a release is **published** (not while it is a draft), and runnable by hand from the Actions tab for an existing tag. Until its key exists (setup below), a channel's workflow builds and checks the package, then skips the publication with a warning instead of failing.

### AUR

[`AUR`](../.github/workflows/aur.yml) publishes `yadbe-bin`, which repackages the `.deb` of the release. [`scripts/aur.mjs`](../scripts/aur.mjs) generates the `PKGBUILD` and `.SRCINFO` with the sum from `SHA256SUMS.txt`; the workflow checks the `.SRCINFO` against `makepkg --printsrcinfo`, builds and installs the package in an `archlinux` container, then pushes both files to `ssh://aur@aur.archlinux.org/yadbe-bin.git`. Pull requests that touch the packaging run every step but the push, on the latest release.

Users install it with `yay -S yadbe-bin` (or `paru -S yadbe-bin`).

To fix the package without a new app version, change the generator, then run the workflow by hand with the same tag and `pkgrel` bumped to `2`.

### Homebrew

[`Homebrew`](../.github/workflows/homebrew.yml) publishes the `yadbe` cask to the third-party tap `SimonVanMello/homebrew-yadbe`. [`scripts/homebrew.mjs`](../scripts/homebrew.mjs) generates `Casks/yadbe.rb` with the sums of `yadbe_<version>_aarch64.dmg` and `yadbe_<version>_x64.dmg` from `SHA256SUMS.txt`; the workflow audits the cask from a temporary local tap (`brew style`, `brew audit --strict --online`), installs and uninstalls it on a `macos-latest` runner, then pushes it to the `main` branch of the tap with the commit message `yadbe <version>`. Pull requests that touch the packaging run every step but the push, on the latest release.

Users install it with:

```bash
brew install --cask simonvanmello/yadbe/yadbe
```

The cask has a `caveats` block that explains how to clear the quarantine attribute, because the app is not notarized (see [Signing](#signing)). Remove it from the generator (between the `BEGIN`/`END quarantine caveat` comments) once notarization lands.

To publish an existing release by hand (first publication, or after a fix to the generator): Actions → Homebrew → Run workflow, enter the tag (`vX.Y.Z`). A run that produces the same cask as the tap pushes nothing.

## Signing

The installers are not code signed yet. The macOS app is only ad-hoc signed (`bundle.macOS.signingIdentity: "-"`, which Apple Silicon requires to run at all); Windows installers carry no Authenticode signature. What users see, and what they do:

- **macOS** (`.dmg` downloaded with a browser): Gatekeeper refuses the first launch ("Apple could not verify “yadbe” is free of malware"). On macOS 15 and later: open the app once, then System Settings → Privacy & Security → "yadbe was blocked…" → **Open Anyway**, and confirm with the password. On older macOS: Control-click the app in Applications → Open → Open. Or, in a terminal: `xattr -dr com.apple.quarantine /Applications/yadbe.app`. The Homebrew cask prints that command. Updates installed by the app's updater are not downloaded by a browser and carry no quarantine attribute.
- **Windows**: SmartScreen shows "Windows protected your PC" for the `.exe` and the `.msi`: **More info** → **Run anyway**. Browsers may also flag the download as uncommon: keep it. The warning fades as the installer gains reputation; each new version starts over.
- **Linux**: nothing to sign; the `.rpm` is not GPG-signed, hence `--allow-unsigned-rpm` for zypper (dnf installs a local file without it).

What code signing would add, and what it needs (not wired yet: a task of its own):

- **macOS**: an Apple Developer Program membership (99 USD a year), a "Developer ID Application" certificate, and notarization. Tauri signs and notarizes during `tauri build` when the build has `APPLE_CERTIFICATE` (the `.p12`, base64), `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`, and either `APPLE_ID` + `APPLE_PASSWORD` (app-specific password) + `APPLE_TEAM_ID` or an App Store Connect API key (`APPLE_API_ISSUER`, `APPLE_API_KEY`, `APPLE_API_KEY_PATH`). The workflow's macOS build would import the certificate into a temporary keychain and pass these as secrets; `signingIdentity` would become the Developer ID, and the cask's caveat goes away. Gatekeeper then opens the app without any step.
- **Windows**: an Authenticode certificate (an OV or EV certificate from a CA, usually on a hardware token or a cloud HSM, a few hundred USD a year; or Azure Trusted Signing, about 10 USD a month). Tauri signs with `bundle.windows.certificateThumbprint` (certificate in the runner's store) or `bundle.windows.signCommand` (any signing tool, e.g. `trusted-signing-cli` or `relic`). SmartScreen then knows the publisher; an EV certificate or accumulated reputation removes the warning.

The updater's minisign signature is independent: it protects in-app updates whether or not the installers are code signed.

## One-time setup by the owner

In this order; none of it can be done from a session, and none of these values may be committed, logged or pasted anywhere but where each step says.

1. **Updater key pair** (required for any release). On a trusted machine:
   ```bash
   pnpm tauri signer generate -w ~/.tauri/yadbe.key
   ```
   Choose a password when asked. This writes the private key `~/.tauri/yadbe.key` and the public key `~/.tauri/yadbe.key.pub`. It must be yadbe's own pair: never reuse yaggui's (its copies would accept yadbe's bundles, and yadbe's copies would refuse them).
2. **Public key into the app**: paste the whole content of `~/.tauri/yadbe.key.pub` (one base64 line) as the value of `plugins.updater.pubkey` in [`src-tauri/tauri.conf.json`](../src-tauri/tauri.conf.json), leave `requireSignedVersion: true`, check it with `node scripts/updater-key.mjs src-tauri/tauri.conf.json` (prints the key ID), and commit it. From then on, release builds are "configured".
3. **Repository secrets** (GitHub → `SimonVanMello/yadbe` → Settings → Secrets and variables → Actions → New repository secret):
   - `TAURI_SIGNING_PRIVATE_KEY`: the content of `~/.tauri/yadbe.key`;
   - `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`: its password.

   Tag builds fail without them; pull request builds skip the updater bundles.
4. **Keep the private key and its password** in a password manager, outside the repository. **Losing them means the installed copies can never update themselves again**: they only accept bundles signed with the key they were built with. A new pair needs a release that users install by hand.
5. **Actions permissions**: Settings → Actions → General must allow GitHub Actions; the release job asks for `contents: write` itself (to create the draft release), so the default read-only token setting is fine unless an organization policy forbids raising it.
6. **Homebrew tap** (optional, for `brew install --cask`):
   1. Create the public repository `SimonVanMello/homebrew-yadbe` (it can stay empty: the first run creates `main`).
   2. Generate a key pair without a passphrase: `ssh-keygen -t ed25519 -N '' -C 'yadbe homebrew tap' -f homebrew-tap`.
   3. On `homebrew-yadbe`, Settings → Deploy keys → Add deploy key: paste `homebrew-tap.pub` and check **Allow write access**.
   4. On `yadbe`, add the repository secret `HOMEBREW_TAP_SSH_PRIVATE_KEY` with the content of `homebrew-tap`. Then delete both local files.
   5. After the first published release: Actions → Homebrew → Run workflow with its tag, if the `release: published` run happened before the secret existed.
7. **AUR package** (optional, for `yay -S yadbe-bin`):
   1. Create an account on <https://aur.archlinux.org> (it becomes the maintainer of `yadbe-bin`).
   2. Generate a key pair without a passphrase: `ssh-keygen -t ed25519 -N '' -C 'yadbe aur' -f aur`, and add `aur.pub` in My Account → SSH Public Key.
   3. Add the repository secret `AUR_SSH_PRIVATE_KEY` with the content of `aur`. Then delete both local files.
   4. The package does not need to exist beforehand: the first push to `ssh://aur@aur.archlinux.org/yadbe-bin.git` creates it. Run Actions → AUR → Run workflow with the tag if the release was published before the secret existed.
8. **Code signing** (optional, see [Signing](#signing)): Apple Developer ID and notarization, a Windows Authenticode certificate; both need workflow changes not made yet.
