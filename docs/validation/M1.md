# Manual validation of milestone M1

Guide to validate M1 on **macOS** and **Windows** before starting M2. Allow about 1 h 30 per OS (three engines). Section 4 lists what was already checked on Linux and how; section 5 gives the performance measurements.

M1 exit criterion (`docs/PLAN.md`): on PostgreSQL, SQL Server and SQLite, the schema is browsable, queries run with streaming results and cancellation, and every statement lands in a searchable history.

The M0 checklist (`docs/validation/M0.md`) still applies to the shell and the connections; this one covers what M1 added. There is no table editing, autocomplete, palette, export or preferences screen yet (M2): "Open data" in the explorer says "Coming with table editing".

Same toolchain as M0 (`docs/validation/M0.md`, section 1). In addition:

|---|---|---|

| SQLite | any `.db` / `.sqlite` file | same |

## 2. Running the app

As in M0 (section 2). Run the checklist **with the debug build with the production CSP** (`pnpm tauri build --debug --no-bundle`), web inspector open (right click → Inspect) to see CSP violations and console errors, then the measurements of section 5 with the release build. Note: `cargo build` / `cargo test` rewrite `src-tauri/target/<profile>/yadbe` without the bundled frontend; rebuild with `pnpm tauri build` before launching that binary.

Create three connections first: **pg** (paste `postgres://yadbe:yadbe-test-pw@localhost:55432/yadbe_test?sslmode=verify-full&sslrootcert=<path to dev/certs/ca.crt>`), **mssql** (paste `sqlserver://localhost:51433;database=m18shop;user=sa;password=Yadbe-test-pw1;trustServerCertificate=true`), **sqlite** (Open a SQLite file → `shop.db`). Then duplicate each one as a **read-only**, **prod**-tagged copy (Duplicate, Edit, Read-only on, Environment prod).

## 3. Checklist

Tick each item, per engine where the line says so (**PG**, **MS**, **SL**). `⌘` on macOS = `Ctrl` on Windows. "Expected" is the correct behavior.

### Connection dialog (F-009, SPEC §9)

- [ ] New connection, PostgreSQL, Host `localhost` — Expected: TLS **Prefer**. Change the host to `db.example.com` — Expected: TLS switches to **Verify certificate**, hint "… the default for a remote host. Choose another mode only if you trust the network." Pick **Require**, then change the host again — Expected: stays **Require**.
- [ ] Edit an existing connection and change its host — Expected: its saved TLS mode never changes by itself.
- [ ] SQL Server, Read-only switch — Expected: hint "SQL Server has no read-only session: a query calling code with side effects … cannot be detected. Connect with a read-only login for full protection."

### Explorer (F-020 to F-023) — PG, MS, SL

- [ ] Double-click the connection — Expected: a query tab bound to it, the tree opens down to its database: **PG** databases `postgres`, `yadbe_test` then schemas; **MS** the database `m18shop` (system databases hidden; the eye button shows them) then schemas `dbo`, `Odd Schema`, `sales`, `shop`; **SL** directly Tables (7), Views (1).
- [ ] Open `shop` → Tables → `customers` → Columns, Keys, Indexes — Expected: columns with type and `NOT NULL`, primary key icon on `id`, the keys and indexes of the fixture; **SL** also Foreign keys, Constraints, Triggers on `orders`. Counts locale-formatted (`1,234` / `1 234`).
- [ ] Filter box: type `cust` — Expected: only the loaded nodes that match, with their ancestors, matched characters highlighted; a match with nothing under it shows a closed chevron. Clearing the filter gives back the tree as it was. With the 500-table schema open, typing stays fluid.
- [ ] Right click `customers` → **Script as → SELECT** — Expected: a new query tab with `SELECT "id", … FROM "shop"."customers" LIMIT 1000;` (**MS** `SELECT TOP (1000) [id], … FROM [shop].[customers];`, **SL** without schema). INSERT / UPDATE / DELETE give templates with placeholders such as `<email, text>` to replace. **Copy qualified name**, **Refresh** (F5) work.

### Running queries (F-041, F-042, F-061, F-062) — PG, MS, SL

- [ ] `⌘↵` on the Script as text — Expected: rows in the grid, "1 statement · 50 rows · N ms" right of the result tabs, the same in the status bar, `Ln 7, Col 11` on the right of the status bar (it follows the cursor; a selection adds "(N selected)").
- [ ] A script of four statements with an error on the third (**PG/SL** `select * from shop.nope where x = 1;`, **MS** batches split by `GO`) — Expected: Result 1, Result 2, then **Messages** selected with the error "relation "shop.nope" does not exist" (**MS** "Invalid object name 'shop.nope'."), "The database rejected the statement.", the statement underlined in red in the editor; **PG/MS** a link "Line 3, column 15" (MS: line of the statement) that puts the cursor there; **SL** "Go to statement 3". **MS** `PRINT 'hello'` shows as an INFO message before the results.
- [ ] Cursor on line 2, `⌘⇧↵` — Expected: only that statement runs, highlighted while it runs. Select a whole line, `⌘↵` — Expected: only the selection runs (the button reads **Run selection**).
- [ ] Streaming and cap: **PG** `select g, md5(g::text) as h, now() from generate_series(1, 1000000) g`, **MS** `SELECT TOP (300000) a.object_id, REPLICATE('x', 100) AS pad FROM sys.all_columns a CROSS JOIN sys.all_columns b`, **SL** a 200k-row table — Expected: first rows within a fraction of a second, the count growing, then "Paused: a result reached its limit" at 100,000 rows: no spinner, the time stands still; the sub-tab reads `Result 1 · 100,000+`. **Load more** → 200,000; **Load all** → everything, "1,000,000 rows". Scroll to the end: the rows load as they come into view.
- [ ] Cell selection with the mouse and Shift+arrows, `⌘C` — Expected: toast "Copied 3 rows as TSV", the clipboard holds tab-separated values (paste it into a text editor). Right click a cell → Copy as CSV / JSON / Markdown / INSERT.
- [ ] Types (**PG**): `select '{"a":[1,2,{"b":null}]}'::jsonb j, '<a><b>x</b></a>'::xml x, '\xdeadbeef'::bytea b, 12345678901234567890.123::numeric n, 9007199254740993::int8 big, null nul, '' empty, '  ' ws` — Expected: numbers exact (no rounding), `NULL` / `empty` / `··` rendered distinctly. Cell viewer (button at the right of the grid footer) on the JSON cell: foldable tree; on the bytes cell: hex and size; **Save to a file…** → native save dialog → the file holds exactly `de ad be ef`.
- [ ] Cancel (`⌘.` or **Cancel**): **PG** `select pg_sleep(30)`, **MS** `WAITFOR DELAY '00:00:30'`, all three a heavy recursive CTE (`with recursive r(n) as (select 1 union all select n+1 from r) select count(*) from r`; **MS** add `OPTION (MAXRECURSION 0)`) — Expected: "Cancelled" within a second; the tab can run again right away. Also cancel a result paused at its cap — Expected: well under a second on a release build.

### Transactions and safety (F-047, F-051, F-008)

- [ ] **PG / MS / SL** Transaction mode **Manual**, run `create table m18_tx(x int); insert into m18_tx values (1);` — Expected: "Transaction open" badge; another client does not see the table. **Rollback** → gone; again then **Commit** → visible from another client.
- [ ] With a transaction open: close the tab — Expected: "Close with an open transaction? Closing rolls the transaction back…", Cancel keeps it. Switch database or connection from the toolbar chip — Expected: "Switch with an open transaction?". Close the window — Expected: the same prompt. **(mac)** ⌘Q goes through the default menu: check whether it asks too (not verifiable on Linux).
- [ ] Auto-commit, `delete from m18_tx` — Expected: "Run a potentially destructive statement?" with "DELETE without WHERE: every row is deleted"; Cancel runs nothing, **Run anyway** runs it. On a prod-tagged connection the guard is always on.
- [ ] Read-only copies: **PG / SL** `insert into …` — Expected: "This connection is read-only: INSERT may change data or the schema. Nothing was run." (lock icon in the history). **PG** a function that writes (`create function public.w() returns int language sql as 'insert into m18_tx values (9) returning 1'` from another client, then `select public.w()`) — Expected: refused by the server, "cannot execute INSERT in a read-only transaction". **MS** `UPDATE …` / `EXEC sp_who` — Expected: refused by the classifier; a statement it cannot see through (a sequence's `NEXT VALUE FOR` inside a function) is the documented limit. Status bar shows a **Read-only** badge.

### Database switcher (F-046)

- [ ] Toolbar chip → Expected: the connections, then the real databases of the server (**PG** `postgres`, `yadbe_test`; **MS** the user databases), a free-text field with **Apply**. Picking another database reopens the tab's session there (explorer and runs follow).

### Files (F-045)

- [ ] **Open a SQL file** (toolbar) → native dialog → a `.sql` file — Expected: a tab named after the file. Edit, `⌘S` — Expected: saved in place, the dirty dot goes away. `⌘S` in an unsaved query tab — Expected: native save dialog, then the tab takes the file name.
- [ ] Change the file from another editor while its tab is open — Expected: "saved.sql changed on disk." with **Reload from disk** / **Keep my version**.

### History (F-100, F-101, F-104)

- [ ] History view of the sidebar — Expected: every statement run above, newest first, grouped by day, with connection tag, duration, row count, status icon (success, error, cancelled, refused).
- [ ] Search `m18_tx` — Expected: only matching entries, the words highlighted. Filters (connection, status, period, min duration) narrow further.
- [ ] Arrow keys select, **Enter** — Expected: opens a new query tab on the same connection and database with the statement. `⌘↵` — Expected: inserts the statement at the cursor of the active editor. Copy, Delete work.
- [ ] Scroll the history far down (run a few hundred statements first), then run a statement in a tab — Expected: the list does not jump nor reload; scrolling back to the top shows the new entry.
- [ ] Clear history (trash icon) — Expected: the dialog says "N entries will be deleted", N locale-formatted; per connection / period scopes.
- [ ] Turn "Record the history" off on a connection — Expected: its statements no longer appear.

### Restore, themes, language

- [ ] Quit with several query tabs (one with a file, one with an unsaved text, one bound to SQL Server) and relaunch — Expected: same tabs, same texts, cursors and scroll; connections not reopened automatically.
- [ ] Switch Light / Dark and English / Français with a result, the cell viewer and the history open — Expected: everything follows at once, syntax colors readable in both themes, no CSP error in the inspector.

## 4. What was checked on Linux, and how

The real app (debug build with the production CSP for the checklist, release build for the measurements) was driven in the Linux container: Ubuntu 24.04, WebKitGTK 2.52, Xvfb with `WEBKIT_DISABLE_COMPOSITING_MODE=1`, no window manager, `tauri-driver` + `WebKitWebDriver` spoken to with plain W3C WebDriver requests. Engines: PostgreSQL 16.15 (TLS, CA from `dev/tls-certs.sh`), SQL Server 2022 (16.0.4305) in Docker, SQLite 3 files, loaded with the fixtures of section 1. In-page listeners recorded CSP violations (`securitypolicyviolation`), console errors and warnings, uncaught errors and every backend event (`connection-state-changed`, `query-progress`, `query-finished`, `transaction-state-changed`, `history-changed`, `statement-logged`, `meta-refreshed`). The GTK file chooser was driven with `xdotool` (Ctrl+L, path, Return). No keychain in the container: passwords were session-only (prompt after a restart).

Gaps found and fixed during this check (task M1-8):

- **Paused run**: a result paused at its cap kept a spinner and a growing elapsed time ("Paused … 49 s") while nothing ran. The clock and the spinners now follow "working" (connecting, running) only.
- **Counts not locale-formatted**: `1000000 rows`, `Result 1 · 1000000`, "N entries will be deleted", explorer counts. A numeric `{count}` is now grouped by `translate()` itself (`1,000,000` / `1 000 000`).
- **"The server rejected the statement."** under a SQLite error: now "The database rejected the statement." for every engine.
- **Explorer filter**: matched tables showed an open chevron over nothing; and every keystroke rebuilt the whole loaded tree (see section 5).
- **Status bar**: no Ln/Col of the editor cursor (SPEC §4): added.
- **TLS default**: Prefer for a remote host; now verify-full (SPEC §9).
- History refetched every loaded page after each run (see `perf(history)` commit); the two "open a tab with text" helpers were merged.

Observed, not changed (follow-ups):

- The result grid sizes its columns from the first window of rows: an integer column of `1…11` is narrow, and `999 985` further down shows as `999…` (double-click the header border fits the loaded rows). A type-based floor for numeric columns would avoid it.
- The final elapsed time of a run that was paused counts the pause ("Cancelled · 6.3 s" after 3 s paused): the backend reports wall-clock time since the start.
- The danger guard shows the statement twice when the script is a single statement (the list of flagged statements, then the whole text).
- A refused or failed history entry shows "0 rows".
- Cancelling a result paused at its cap on SQL Server drains the rows already on the way (TDS): 0.3 s in release, about 3 s in a debug build.
- A server statement error is shown with the server's own text and the generic "The database rejected the statement."; `25006` (read-only transaction) could get a catalog entry pointing at the read-only setting.

Not verifiable here (to check on macOS / Windows): GPU rendering and scrolling smoothness with a real compositor; WKWebView (macOS) and WebView2 (Windows) specifics, including the CodeMirror input methods, clipboard permissions and the native `<select>` popups; the native open / save dialogs' look and modality; real macOS Keychain / Windows Credential Manager with SQL Server passwords; Azure SQL, SQL Server named instances (`host\instance`, SQL Browser), Windows authentication (not supported yet); remote TLS with the OS trust store (a cloud PostgreSQL or Azure SQL with *Verify certificate* and no custom CA); keyboard shortcuts with the macOS `⌘` mapping (`⌘.` cancel, `⌘⇧↵`); the window title and dirty markers in the macOS window menu.

## 5. Performance measurements

Results in the Linux container (Xvfb, software rendering, WebKitGTK 2.52, database on localhost; **not** the reference machine of SPEC §3).

| Measure | Scenario | Result | Target |
|---|---|---|---|
| P-01 start → interactive window | release, disk cache dropped, 10 launches: welcome / restore (1 SQLite connection, 3 query tabs) | median **680 / 741 ms** (599–895 / 647–809) | < 800 ms ✅ (thin margin) |
| P-01 | same, warm cache | median 600 / 668 ms | < 800 ms ✅ |
| P-02 connect → tree shown | release, real app, PG database with a 500-table schema, fresh frontend cache, 6 runs | connect 22–44 ms, then first level (databases + schemas) drawn **67–104 ms** after `connected` | < 400 ms ✅ |
| P-02 | same, open the 500-table schema then Tables (500) | 45 ms + 57 ms to the first table row | |
| P-03 query sent → first rows painted | release, real app, PG `select generate_series(1, 1000000), 'x'` (streams from the first row), 5 runs | **55–72 ms** after Run (first rows event at 7–15 ms) | < 200 ms over the server's first row ✅ |
| P-03 | `select g, md5(g::text) from generate_series(1, 1000000) g` (the server materializes the function before its first row) | first rows at 63–106 ms (server), painted at 107–168 ms: **45–60 ms over the server** | ✅ |
| P-03 | 100k × 50 `select * from p04_grid` | first rows painted 89–159 ms; whole result 2.1–2.2 s | |
| P-04 grid scrolling 100k × 50 | real app, release, WebKitGTK (`pnpm perf:grid:webkit`) | vertical 62.5 fps, max 24–31 ms; horizontal 62.5 fps, max 28–32 ms; 0 frame > 32 ms | 60 fps, no frame > 32 ms ✅ |
| P-04 | Chromium, mock (`pnpm perf:grid`), CPU ×1 | 59.9 fps, max 16.8 ms; random jumps: 2 frames of 50 ms while windows load | ✅ (jumps indicative) |
| P-07 tab switch, query tabs with editors | `pnpm perf:tabs`, CPU ×1 / ×4 | median **20.4 ms** (p95 24.1, max 43.3) / 45 ms | < 50 ms ✅ |
| P-08 history search, 100k entries | `cargo test --release --test history_bench p08` | worst case **27 ms** (common word + errors only + connection) | < 100 ms ✅ |
| Explorer filter, 10 000 objects | `pnpm perf:explorer`, `table_01` at once, CPU ×1 / ×4 | **51 / 81 ms** (before M1-8: 103 / 369 ms) | |
| Explorer filter | typing `table_03` a key at a time, CPU ×1 / ×4 | median **22.6 / 66 ms** per keystroke (before: 35–79 ms at ×1) | |

Notes:

- **P-01** grew by 50–140 ms since M0 (630 / 602 ms cold), mostly CodeMirror and the grid in the main bundle: still under target here, so the editor is not lazy-loaded yet; if the reference machine passes 800 ms on the restore scenario, lazy-loading `SqlEditor` (and the grid) is the first lever.
- **100k × 50 in 5–7 s on a debug build**: in release the first rows are painted in ~0.1 s and the whole result is stored in 2.1 s. The time is in the backend: the PostgreSQL driver alone takes 1.16–1.26 s to decode the 5 million values to `Value`s (formatting numerics and timestamps as strings, by design: they cross the IPC as text), the runner and the `ResultStore` 0.3–0.7 s more; `psql` reads the same rows in 0.74 s. Nothing in the IPC or the rendering path: the grid only fetches the visible 500-row windows. The debug build is slower because the decoders run unoptimized.
- **Explorer filter**: the whole loaded tree was rebuilt on each keystroke (one `getQueryState` per loaded table: default options + key hashing); it is now built once per change of the data or of the expanded nodes, a longer query prunes the previous result, and the cache is read in one pass. The per-keystroke figure includes one frame of measurement floor.

Reproduce on the reference machine:

```bash
pnpm tauri build --no-bundle
pnpm perf:startup [--drop-caches]       # P-01 (headless Linux: xvfb-run -a)
pnpm perf:tabs                          # P-07
pnpm perf:grid                          # P-04, Chromium
YADBE_TEST_PG_URL=… pnpm perf:grid:webkit --binary src-tauri/target/release/yadbe   # P-04, real app (Linux)
pnpm perf:explorer                      # explorer tree and filter
cd src-tauri && YADBE_TEST_PG_URL=… cargo test --release --test introspection p02 -- --ignored --nocapture
cd src-tauri && YADBE_TEST_PG_URL=… cargo test --release --test query_postgres p03 -- --ignored --nocapture
cd src-tauri && cargo test --release --test history_bench p08 -- --ignored --nocapture
```

In the app, with the web inspector: P-02 is the time from the double click on a connection to its databases and schemas drawn; P-03 the time from Run to the first rows painted, compared with the server's time to the first row (`\timing` in `psql` with `\set FETCH_COUNT 1`). On macOS / Windows, include the output of the `pnpm perf:*` commands in the report.
